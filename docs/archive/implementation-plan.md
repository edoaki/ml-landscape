## 1. 推奨する使い方

**統合用のウィンドウを1つ残し、本文用を最大3つ並行して使う。まずS00だけを実行し、共通基盤と移行見本の検証を終えてから本文を開始する。** 本文の27タスクは27ウィンドウを同時に開く意味ではない。完了した枠に次のタスクを入れる。大きく異なる主題へ切り替えるときは、新しいCodexタスクを同じウィンドウで開くと担当範囲が混ざりにくい。

画像・動画・3Dはすでに説明・図・操作が充実している。新規執筆と同じ扱いにせず、保持・分離・移行を主目的にする。音声、時系列、推薦、モデル詳説、XAIにも同じ方針を適用する。ただし、移行後の再検証は必要であり、完成済みだから作業ゼロとはしない。

各指示ファイルは単独で貼れるように共通条件も含めた。ファイルの内容を貼るか、下記の一文で依頼する。

> docs/implementation-prompts/M01.md を読み、そこに書かれた担当範囲と完了条件に従って実装してください。

`M01`を開始するタスクIDへ置き換える。G0成立後、共通基盤を含む同じ開始コミットから各専用Worktreeを作る。以後は統合担当が提示する最新の開始コミットを使う。本文同士は他担当の未統合ブランチを開始地点にしない。

別ウィンドウだけでは作業ファイルは分離されない。並行する本文タスクはそれぞれ専用Worktreeを使う。Worktreeを使っても共有ファイルを同時に編集すれば統合時に競合するため、以下の所有範囲も守る。[OpenAI公式のWorktree説明](https://developers.openai.com/ja-JP/docs/environments/git-worktrees)

## 2. 現状から見た作業の違い

今回確認したのはsourceの構成、本文の該当箇所、QA.mdの履歴、既存のテストである。全ページを再度ブラウザで検証したという意味ではない。QA.mdには過去の構成や後に削除した要素も含まれる。現在の本文と新しい記録を優先する。

| 部分 | 現在の材料 | 今回の主作業 |
|---|---|---|
| 画像 | 分類・回帰・検出・領域分割・深度・姿勢の図と説明 | ほぼ保持してMarkdownへ移し、分散した研究例を回収 |
| 動画・3D | SAM 2のフレーム操作、RAFT、SLAM、点群、3DGS、NeRF、Sora、Genieの図・動画 | 動画と空間へ分離。現行の素材・操作を維持 |
| 音声 | 比較試聴、音源切替、波形等 | 再生位置維持を含めて移行 |
| 時系列・推薦 | 予測・異常検知の操作、推薦の具体例 | 独立ページへ分離。グラフ側の短い説明は補強 |

| 意思決定・科学 | ゲーム・ロボット・経路、生命・物理・気象の結果例 | 例を回収して分割し、計画で追加した方法・条件を補う |
| 学習・信頼性・効率化 | 一覧や短い説明と、一部の図・操作 | 独立ページの説明へ拡充 |
| 安全性・公平性・因果・情報幾何・データ評価等 | 主に収録計画 | 新規執筆中心。既存材料があると仮定しない |

同じ移行でも、Flow Matching等の操作が多いページは独立タスクにする。逆に音声・時系列・推薦・グラフは1担当内で順に処理できる。本文タスクの大きさはページ数の均等化ではなく、移行の複雑さと説明境界で決める。

## 3. 最初に実行すること：S00と開始条件G0

統合用ウィンドウへ [S00の指示](implementation-prompts/S00.md) を投げる。この間は本文の実装を並列開始しない。読み取り専用の調査は可能だが、必須ではない。

S00は以下を完成させる。

1. 現状の保存。現時点では初回コミットがないため、リポジトリルート・追跡対象・除外設定を確認して初回コミットを作る。以降の基盤作業をその上に記録する。
2. Markdown、メタデータ、ページID参照、出典、素材、専用部品の形式とビルド・検査手順を実装する。
3. 目次と予定ページの管理を作り、本文未着手と公開可能を区別する。未完成ページを完成した教材として公開しない。部分実装の検証と、最終版の欠落検査を分ける。
4. `vision`を実ページの移行見本として完成させる。数式・SSM操作・音声・動画は既存の代表要素を検証用fixtureへ取り出し、新方式で確認する。fixtureは教材本文に混入させない。
5. 共通の編集契約を `docs/implementation-contract.md` に保存し、基盤をコミットする。現在の計画書のハッシュと更新内容も記録し、並行して計画が更新された場合の差分を検出できるようにする。

**G0の成立条件**：上記が実装・検証され、各担当が共通コードを編集せずにページと専用部品を追加できる。少なくともMarkdown本文、数式、静止図、ローカル動画・音声、操作部品、出典参照、HTML直接表示・オフライン・JS無効時の基本表示が確認されている。新形式の見本・コマンド・開始コミットIDが提示されている。文書だけ出来ていてビルドが未実装ならG0未成立。

`vision`のS00成果はM01へ引き継ぐ。M01は完成部分を再執筆せず、残る研究例統合・ページ分割・最終確認を担当する。

## 5. 並列に投げてよい範囲と推奨投入順

**必須の依存は「S00 → G0 → 基礎・モデルの整備 → G1 → 分野・横断研究の追加 → 最終統合」。** 更新された設計書の「基礎とモデルの基本説明を整えた上で追加分を執筆する」という順序を採用する。標準の読む順序も、はじめに→基礎→モデル→分野・タスク→横断研究とする。

- **G0後に並列開始可**：E06・E07・E17とM03〜M08。互いの完了待ちは不要。
- **G0後に先行してもよい保持移行**：M01・M09。既存の説明を保つ移行であり、新規の分野説明を大きく増やす作業とは分ける。
- **G1後に並列開始可**：残りのE担当とM02。M02にはグラフの独立化・補強が含まれる。
- **G1の成立条件**：E06・E07・E17とM03〜M08を統合し、基礎とモデルの基本説明が計画の到達点を満たし、新しいビルドで読めることを統合担当が確認した。モデル各ページは基本説明から詳説へ進める。基礎の先行読書だけに依存せず、個別ページの用語補足も確認する。

次は本文用3ウィンドウを使う場合の推奨順。G0〜G1内、およびG1後の各段階では、同じ行の全員が終わるまで待つ必要はなく、空いた枠に同段階の未着手タスクを入れてよい。開始コミットは統合担当が指定する。

### 同時に行わない作業

- S00の編集形式・部品API変更と、その形式に依存する本文実装。
- 同じタスクID／同じページを二つのウィンドウに割り当てること。
- 別タスクによるnavigation.yml、共通CSS/JS、ビルド、共有素材台帳、計画書の同時編集。
- 同じローカルチェックアウトでの複数ビルド・生成・コミット。専用Worktreeの各ビルドは並列でよい。
- 統合先で複数の取り込み操作を同時実行すること。取り込みは1件ずつ行う。
- 旧source/・assets/の削除や大規模整理と、そこからの本文移行。削除は全移行の確認後。

共有の仕様変更が避けられないと分かったら、統合担当が影響するタスクへ変更点を知らせ、その部分の編集を止めて基盤修正を先に取り込む。各担当は保存・コミット後に更新された基盤を取り込み、担当の検証を再実行する。無関係な本文作業まで止める必要はない。

## 6. ファイル所有権と共有素材

| 対象 | 編集する担当 |
|---|---|
| navigation.yml、ビルド、テンプレート、styles、共通部品、全体テスト | S00／統合担当のみ |
| content/<区分>/<ページID>/（本文、media、sources） | ページの担当のみ |
| components/pages/<ページID>/、scripts/pages/<ページID>/、tests/pages/<ページID>/ | ページの担当のみ。S00が宣言式の読込を用意 |
| content/shared/、旧素材の移行台帳 | 統合担当のみ。本文担当は登録済み素材を参照 |
| docs/implementation-status/<タスクID>.md | 当該タスクのみ |
| docs/content-plan.md、全体進捗・README・QA | 統合担当のみ。各記録を反映 |
| source/、assets/、旧ルートHTML | 移行中は全本文担当に対し読み取り専用 |
| dist/等のビルド出力 | 各Worktreeで生成可。直接編集せず、コミット方針は実装契約で統一 |

既存assetsはS00が新ビルドから不変参照できる置き方とURL解決を用意する。大量の動画・出典を各担当が無秩序にコピーしたり、旧assets/README.mdへ全員で追記したりしない。共有される出典の登録は中央、ページ固有の新規出典は各sources.ymlとする。重い素材生成は通常の本文ビルドから分離する。

## 9. 統合用ウィンドウの指示

各担当が終わったら、統合用ウィンドウへ [S90の指示](implementation-prompts/S90.md) を投げ、末尾に担当ID・ブランチ名・コミットIDを添える。複数担当分をまとめて渡しても取り込みは一つずつ行う。担当のコミットが完了したら、そのWorktreeで追加編集しない。修正が必要になったら、最新の統合状態を基に明示的に再開する。

統合担当は担当記録を読んで差分を確認し、共通ファイルの無断変更や説明境界の矛盾を確認する。変更後の担当範囲を検証し、取り込み後に全体の整合性を検査する。content-plan.mdの移行元・実装状況を反映するのはここだけ。

最後に [S99の指示](implementation-prompts/S99.md) を投げる。introduction、旧URL案内、研究例の回収、全ページの欠落・重複、出典・表示・操作・オフライン・直接表示を確認する。旧optimization.htmlは組合せ最適化の案内だが、新ページID optimization は学習の最適化なので、安定IDとURLを分離して既存リンクの意味を保つ。

既存の標準検証は `python3 -m unittest discover -s tests -v` と `node tests/test_ssm_animation.cjs`。現行テストには旧配置に依存するものがあるため、新配置への対応はS00／統合担当が行う。成功件数だけを引き継がず、新しい成果物と部品を実際に検査する。本文の制作側確認と、B3相当の読者による試読は別記録とし、未実施の試読を完了条件の達成として報告しない。
